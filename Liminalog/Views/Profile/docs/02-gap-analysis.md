# 02. 仕様とのギャップ分析

> [01-current-architecture.md](01-current-architecture.md) で抽出した現状実装と、`Liminalog/liminalog_spec_v04.md` の差分を洗い出す。
> ギャップは「未実装」「解釈ズレ」「仕様の曖昧さ」「アーキ的負債」の 4 種に分類する。

凡例:
- 🔴 **解釈ズレ** — 実装はあるが仕様と違う動きをしている
- 🟡 **未実装** — 仕様にあるが実装されていない（Phase想定通りも含む）
- 🟠 **仕様曖昧** — 仕様書だけでは実装判断ができない部分
- 🟣 **アーキ負債** — 仕様には書かれていないが、将来詰む構造的問題
- 🟢 **仕様超過** — 仕様にないが実装で追加されているもの

## 1. データモデルのギャップ

| 領域 | 仕様 | 現状 | 分類 |
|------|------|------|------|
| Chapter | `photoData: Data?` を持つ | フィールドなし | 🟡 未実装 |
| Chapter | `categoryId: UUID` で参照 | `category: Category?` 直接参照（双方向Relationship） | 🟢 仕様超過（妥当な改善） |
| Friend | 仕様書のディレクトリ構成に記載 | モデル未定義 | 🟡 未実装（Phase 3想定） |
| PublicSettings | 仕様書のディレクトリ構成に記載 | モデル未定義（`VisibilityPreset` が代替か?） | 🟠 仕様曖昧 |
| UnlockItem | 仕様書のディレクトリ構成に記載 | モデル未定義 | 🟡 未実装 |
| VisibilityPreset | 名称・実装が独自 | `level: {all,partial,none}` 程度の薄い実装で未使用 | 🔴 解釈ズレ（仕様は「仲良し/知り合い/オフ/カスタム」） |
| CategorySet | 仕様に記載なし | 「平日/休日」など8件のカテゴリ束。グリッド切替に使われる | 🟢 仕様超過 |
| PlanBlock | 仕様書にPlanモデル明示なし | スコア計算に必要な「予定」をSwiftDataで持つ | 🟢 仕様超過（必要な追加） |

### 仕様超過の妥当性
- **CategorySet** は仕様書の「グリッドは最大8個」「使用頻度順に自動並び替え」「9個以上は『もっと見る』」を、**手動の文脈切替（平日/休日）** に置き換えた独自設計。仕様意図と部分的に矛盾する可能性あり → [03-architecture.md](03-architecture.md) で判断
- **PlanBlock** はスコア計算を成立させるために必須。仕様書のスコア仕様は「予定」と「実績(Chapter)」の比較を要求しており、予定を持つストレージは不可欠

## 7. アーキテクチャ的負債 🟣

仕様書には書かれていないが、現状の作りのまま Phase 2/3 に進むと辛くなる点。

### 🟣 ChapterStore の God Object 化
- 378行・約30メソッドに「Chapter / Category / CategorySet / PlanBlock / Score / Streak / Seed / LiveActivity」全部が同居
- Phase 3 で CloudKit / CKShare / Friend / Reaction / Comment が加わると倍々で膨らむ
- → ストア分割の判断が必須 ([03-architecture.md](03-architecture.md))

### 🟣 revision カウンタ依存
- SwiftData の `@Query` を全面採用していないため、`store.revision` を手動でインクリメントし `onChange` で再フェッチする方式
- 通知漏れ・無駄な再描画の温床。CloudKit からの非同期更新が来た場合に統一的に扱えない
- → SwiftData `@Query` 中心への移行か、Observation の正しい使い方への矯正が必要

### 🟣 ウィジェット ↔ アプリのデータ共有なし
- App Groups 未設定。ウィジェットは SwiftData ストアに触れない
- Live Activity は ActivityKit の `ContentState` にカテゴリ一式を inline コピーすることで回避しているが、これは記録グリッドウィジェットには使えない手法
- → App Group + 共有 ModelContainer の設計が Phase 1 完了に必須

### 🟣 CloudKit ストア URL 未指定
- `LiminalogApp.modelContainer(for:)` でローカル専用ストアを宣言済み
- Phase 3 で CloudKit 同期を後付けする場合、ストアの移行が発生する
- 最初から CloudKit-compatible スキーマ + `.private` データベース指定にしておくと移行不要

### 🟣 Color(hex:) の二重実装
- アプリ側 (`Extensions/Color+Hex.swift`) とウィジェット側 (Live Activity 内 private) で別実装
- 共有フレームワーク (Swift Package or 内部 Framework target) がない
- → コード共有戦略を [03-architecture.md](03-architecture.md) で決める

### 🟣 テスト 0 件
- スコア計算・ストリーク・1分ルールなど純粋ロジックが unit test 対象として最適なのに、テストターゲット自体なし
- → [06-testing.md](06-testing.md) で扱う

### 🟣 #if DEBUG seed が実機 DEBUG ビルドにも入る
- `RootTabView.task` で `#if DEBUG seedPreviewPlansIfNeeded` を呼んでいる
- 実機の開発ビルドで「いきなりダミー予定が入る」状態
- → プレビュー専用に分離するか、ENV変数ゲート化

### 🟣 `Calendar.japanese` という未定義参照
- `CalendarView.swift` で `Calendar.japanese` を使用しているが、コードベース内に定義が見当たらない
- ビルドが通る前提だと、`Date+Formatting.swift` などに extension があるはず → 要確認
- 未確認なので 🟠 仕様曖昧 にも該当

| デザイン | 「カラフル・エネルギッシュ」の具体的トーン（カラーシステム未定義） |
| デザイン | カテゴリカラーのカスタム範囲（任意の Hex？プリセット選択？） |

| グリッド | 「もっと見る」展開時の UI（モーダル？インライン？） |

| 友達 | 「リアクション」の絵文字パレット（カスタム可？） |
| 友達 | ランキングのタイブレーク（同点時の順位） |

→ 全部を一度に確定する必要はないが、Phase 1 完成までに最低でも「公開設定」「グリッドのもっと見る」を確定する必要あり。

## 9. ギャップサマリー（優先度付き）

### 🔴 高優先度: Phase 1 完了のブロッカー
1. ウィジェット記録グリッド + App Groups
2. 公開設定 UI（最低限のトグル）
3. 「もっと見る」展開の確定 + 実装

### 🟠 中優先度: Phase 2 設計までに解決
1. CloudKit ストア前提でのスキーマ確定
2. ChapterStore の分割方針
3. SwiftData `@Query` への移行 or revision の正当化
4. 1日の始まり時間 → 全コードの startOfDay 依存箇所の置換
5. 設定画面の本格実装

### 🟡 低優先度: Phase 3 設計時に再検討
1. Friend / Reaction / Comment / GroupChallenge モデル
2. 公開設定プリセットの本格実装
3. カテゴリマッピング
