# 27. 予定編集の透明化モデル（編集ロック緩和・当日変更マーク・計画キープバッジ）

カレンダー機能がアプリのコアに育ってきたため、一般カレンダーの代替として成立する操作感を目指す。その障害になっている「今日以前の予定・前日以前の実績を変更できない」現行ロック（spec v0.4「スコア公平性のための編集ロック」）を、**技術的に禁止する方式から、変更を許可して見える化し、守った人を評価する方式**へ転換する。

2026-07-19 ユーザー決定済み。設計背景・却下案も含めて本ドキュメントが正。spec v0.4 の該当節はこのドキュメントへの参照に置き換え済み。

> ステータス：**Codex プランレビュー待ち → 実装可**。タスク分解は AI_TASKS §8.15。

---

## 0. 決定の背景（なぜロックを緩めるか）

- ユーザーの声:「予定は朝に決まるので、当日に今日の予定を組みたい・変更したい」。現行ロックでは当日の予定操作が一切できず、カレンダーとして致命的。
- 振り返りアプリなのに、寝落ち等で壊れた昨日の実績を恒久的に直せないのは、公平性のためにコア価値（正確な振り返り）を削っている。
- 本アプリの公平性思想はもともと「正直さは友達というフィルターが担保する」（spec の前提条件）。記録の捏造は技術的に防いでおらず社会的信頼に委ねているのに、タイミングだけ技術ロックで縛るのはバランスが悪い。**技術で守る範囲を絞り、透明化（マーク）と報酬（バッジ）で残りを守る。**
- 却下案: rolling lock（過ぎた時間帯の予定だけ物理的にロック）。朝プランニングは解決するが「原則は前日までに組む」という規範を仕組みで表現できないため、マーク+バッジ方式を採用した。

## 1. ルールセット（正）

ゾーンは 0:00 区切り（DayBoundary 基準。1日の始まり時間は全員 0:00 固定の現行仕様のまま）。

| ゾーン | 予定（時間つき） | 実績（Chapter） |
|---|---|---|
| 明日以降 | すべて自由（マークなし） | — |
| 今日 | すべて自由。ただしスコア関連操作に**当日変更マーク** | 自由（現行どおり・マークなし） |
| 昨日 | **削除のみ可**（マーク）。時間・カテゴリ変更、新規追加は不可 | 修正・追加・削除可。時間系の修正に**後から修正マーク** |
| 一昨日以前（確定） | **削除のみ可**（説明ダイアログ+マーク）。時間・カテゴリ変更、新規追加は不可 | ロック（メモ・場所・公開設定のみ現行どおり編集可） |

- 「スコア関連操作」= 追加・開始/終了時刻の変更・カテゴリ変更・削除（ドラッグでの移動・リサイズを含む）。タイトル・メモ・公開設定・重要フラグの変更は対象外（マークなし・バッジ影響なし）。タイトルは新たに過去分も編集可にする（スコア無関係のため）。
- 時間未指定の重要予定（`isAllDay == true`）はスコア外なので現行どおり全期間で自由。時間つきへの変換はスコア対象化するため「新規追加」と同じ扱い（今日まで・マーク付き。過去日への変換は不可）。
- 過去日への時間つき予定の新規追加は引き続き禁止（docs/26 Item D の past-plan-guard ポリシーを維持。後付けプランの温床のため）。
- 日またぎ予定の所属日はその予定の開始日（`dayStart(startTime)`）で判定する。
- 予定を別の日へ移動する操作は「元の日から削除 + 先の日へ追加」として扱う（両日のルール・マーク判定を適用。昨日以前が絡む移動は不可、削除のみ）。

### 受け入れ観点

- 当日の朝に今日の予定を新規作成できる。当日の未来時間帯・過去時間帯どちらの変更もできる（マークは付く）。
- 昨日の実績（例: 閉じ忘れた睡眠チャプター）を今日中に修正できる。
- 一昨日以前の予定を削除してもスコア・ストリーク・累計・過去日のスコア表示が1点も動かない。
- 一般カレンダーとの操作差は最終的に「過ぎた日の予定は時間を動かせない（消すことはできる）」の一点に収まる。

## 2. 当日変更マーク

- **目的**: 変更は自由にする代わりに、後付け・組み替えが友達（と自分）から見えるようにする。
- **対象**: その予定の所属日 0:00 以降に行われたスコア関連操作。
  - 当日以降に新規追加した予定 → 「当日追加」（`createdAt >= 所属日のdayStart` で導出。新規フィールド不要）
  - 当日以降に時間・カテゴリを変更した予定 → 「当日変更」（新規フィールド `sameDayScheduleEditedAt: Date?` に記録）
  - 削除はモノが消えるため予定単位でなく日単位のフラグに記録（§4 の `planTouchedSameDay`）
- **表示**: 予定カード・詳細に小さいマークアイコン。日単位の「当日変更あり」はデイビュー・友達から見た日ビュー・**ランキング行**に表示する。ランキングに出すことで「無印の90点とマーク付きの95点のどちらを信用するかは友達が判断する」という友達フィルター思想が完成する。
- 前日までの操作（明日以降の予定をいじる）は何をしてもマークなし。

## 3. 計画キープバッジ

- **条件**（日単位・全て満たす）:
  1. 前日までに組んだ時間つき予定がその日に1件以上ある（`createdAt < dayStart` の存在で判定。予定ゼロの日が自動でバッジ獲得になるのを防ぐ前提条件）
  2. その日の予定集合にスコア関連操作が一度も行われていない（`planTouchedSameDay == false`）
- **確定タイミング**: その日のスコア確定と同時（= 一昨日になった時点、§5）。確定までの間（当日・翌日）は削除でバッジが外れうる。昨日の予定を消して「計画キープ」の見た目だけ残す抜け道を塞ぐため。
- **保存**: `DailyScoreSnapshot` に `planKeptDay: Bool` を追加（morningPersonaDay 等の既存フラグ群と同じ基盤・同じ確定タイミング）。
- **表示**: デイリーカード・ランキング行・プロフィール。デイリーカードのパターン検出（DailyCardPatternDetector）への組み込みは任意の後続。
- 将来のチューニング候補（v1 では実装しない）: 2段階制（前日組み=金 / その日の最初の記録開始前までに組んだ分=銀）。朝プランニング勢が毎日バッジなしで萎える兆候が出たら検討。

## 4. バッジ喪失の注意ダイアログ

**気づかないでバッジを失うのがストレス**なので、外れる操作の1回目だけ事前に注意する。

- **発火条件**（3つ全部揃ったときのみ）:
  1. 対象日がバッジ有資格（前日までに組んだ予定がある）
  2. まだ未タッチ（`planTouchedSameDay == false`）
  3. 操作がスコア関連（§2 と同一判定）
- **抑制**: 一度「変更する」を選んだら `planTouchedSameDay = true` を立て、**その日への以降の操作では二度と出さない**。フラグは CloudKit 同期に乗せ、複数端末でも一貫させる。
- この条件設計により、朝プランニング勢（0:00 時点で予定ゼロ = バッジ資格なし）には一度も出ない。出るのは「前日に計画した人が、それを崩そうとした最初の瞬間」だけ。
- **確定済みの日**（一昨日以前）の削除は注意ではなく説明ダイアログに切り替える:「この日のスコアは確定済みのため変わりません」。原則 =「操作に実害があるときだけ警告、実害がなくなったら説明」。ダイアログは常に最大1種類・その日1回。
- **文言たたき台**（責めないトーン。変更は自由であることを明示）:
  > この日の「計画キープ」が外れます。変更は自由で、当日変更として記録されます。変更しますか？
  - ボタン: 「変更する」/「やめる」。「やめる」で予定もバッジも無傷。
- ドラッグ操作（移動・リサイズ）は**ジェスチャ確定時にコミット前確認**とする（ドラッグ開始時に出すと操作を分断する）。「やめる」なら元位置へ戻す。
- 「今後表示しない」のグローバル設定は v1 では作らない（出るのは1日最大1回・前日計画した日だけで頻度が十分低い）。

## 5. スコア計算の変更

### 5.1 確定の1日遅延

- 実績が昨日まで編集可能になるため、**スコア確定境界を「昨日以前」から「一昨日以前」へ1日ずらす**。
- 今日・昨日 = ライブ計算（編集で動く）。一昨日以前 = `DailyScoreSnapshot` 確定台帳（不変・再計算しない）。
- 累計 = 確定台帳 + 昨日ライブ + 今日ライブ。ストリーク・アンロック判定も同じ境界で扱う（昨日はライブ値で判定）。
- ランキングは「今日」タブが終日動き続ける現行体験と同型で、「昨日」タブも動きうるようになる。後から修正マーク（§6）で可視化する。

### 5.2 分母ラチェット（削除で得をしない保証)

- 日ごとに「その日の予定総量（0:00-24:00 クリップ後 plannedDuration）の当日中の最高値」を保持し、**スコアの分母は `max(現在の予定総量, 最高値)`** を使う（カテゴリ達成率・時間軸一致率の両分母）。
- 効果: 予定の追加は分母を上げ、削除・縮小は下げない。分子（達成分・一致分）は現存予定からのみ発生するため、**削除でスコアが上がる経路が機械的に消える**。マークが「見える化」、ラチェットが「得させない」の役割分担。
- ラチェット値の更新はスコア計算パスで行い、確定と同時に固定される。

### 5.3 確定日のスコア表示をスナップショット読みへ切替（削除解禁の前提条件）

- 現状、カレンダーの日別スコアバッジや期間集計は確定日も含めて**毎回ライブ計算**（`ScoreStore.summaries` → `ScoreCalculator.summary`、`CalendarDayScoreCache` はシグネチャキャッシュ）。このままだと過去の予定を削除した瞬間に過去日の表示スコアが動き、確定台帳（累計）と矛盾する。
- **確定日（一昨日以前）の表示・統計は `DailyScoreSnapshot` を読む**ように切り替える。ライブ計算は今日・昨日のみ。`CalendarDayScoreCache` のコメントにある「毎回回すと重い」問題の解消にもなる。
- ダッシュボードの期間集計のうちスコア系は同様にスナップショット基準へ。時間集計（カテゴリ別合計など）は実績ベースなので現行のままでよいが、確定日の実績は編集不可なので結果的に安定する。

## 6. 実績側の変更

- `ChapterStore.isChapterTimeLocked` の境界を「今日より前」から「昨日より前」へ1日ずらす（今日+昨日が編集可）。
- 昨日分のチャプターに対する時間・カテゴリ・追加・削除の操作時、`lateEditedAt: Date?`（新規フィールド）を刻み、「後から修正」マークとして表示する（友達から見えるタイムライン・自分のデイビュー）。spec v0.4 が予告していた監査表示の実装。
- 当日中の実績編集は現行どおり自由・マークなし（リアルタイム自己申告は通常操作のため）。
- 追加も許可対象（昨日ログを忘れた分を翌日入れられる）。追加された昨日分にも `lateEditedAt` を刻む。
- 一昨日以前は現行どおりロック（メモ・場所・公開設定のみ編集可）。

## 7. データモデル・実装ポイント

### 新規/変更フィールド

| 対象 | 変更 | 用途 |
|---|---|---|
| `PlanBlock` | `sameDayScheduleEditedAt: Date?` 追加 | 当日変更マーク（当日追加は `createdAt` から導出） |
| `Chapter` | `lateEditedAt: Date?` 追加 | 後から修正マーク |
| `DailyScoreSnapshot` | `planKeptDay: Bool` 追加 | 計画キープバッジ（確定値） |
| 新規 `@Model PlanDayState`（名称は実装判断） | `dayStart` / `dayIdentifier` / `planTouchedSameDay: Bool` / `plannedDurationHighWater: TimeInterval` | ライブ日（今日・昨日）の触った判定・ダイアログ抑制・ラチェット。確定時に planKeptDay / スコアへ反映 |

- すべて CloudKit 互換（全プロパティにデフォルト値・unique 制約なし・`LiminalogSchema` へ登録）。追加のみでマイグレーションは軽い。
- 削除はモノが消えるため、削除時に `PlanDayState.planTouchedSameDay` を立てることで日単位に記録する（予定単位のトゥームストーンは作らない）。

### 判定の一元化（最重要）

- **マーク対象・バッジを外す操作・注意ダイアログ対象の3つは必ず単一の述語**（例: `PlanEditPolicy.isScheduleAffectingChange`）**を共有**する。別々に実装すると「マークは付いたのに注意が出なかった」というズレが必ず出る。
- ロック判定も同様に policy 型へ集約（リポジトリ慣例の「テスト可能な型に切り出す」）: 予定側 = 追加可否・時間/カテゴリ編集可否・削除可否 × ゾーン、実績側 = 境界1日シフト。

### 触る箇所（現行コードのアンカー）

| ファイル | 現状 | 変更 |
|---|---|---|
| `Stores/PlanStore.swift` `isScheduleLocked` / `canCreate` | 日付単位で今日以前を全ロック | ゾーン×操作種別の新ポリシーへ差し替え。削除許可・当日操作許可・過去日追加禁止の維持 |
| `Stores/ChapterStore.swift` `isChapterTimeLocked` | 前日以前ロック | 境界を1日過去へ + `lateEditedAt` 刻印 |
| `Stores/ScoreStore.swift` `reconcileFinalizedDailyScores` ほか | 昨日以前を確定台帳へ | 境界を一昨日以前へ。累計/ストリークは確定+昨日ライブ+今日ライブ。`summaries` は確定日をスナップショット読みへ |
| `Stores/ScoreCalculator.swift` | 分母 = 現在の plannedDuration | ラチェット値を受け取り `max()` を分母へ |
| `Stores/CalendarDayScoreCache.swift` | 全日ライブ計算+シグネチャキャッシュ | 確定日はスナップショット読み（キャッシュ不要化） |
| 予定編集 UI（`PlanCreateSheet` / 編集シート / `TimelineDragPolicy` 系） | ロックで操作不能 | 注意ダイアログ（コミット前確認）+ マーク表示。docs/26 Item D の past-plan-guard は維持 |
| ランキング行 / デイリーカード / デイビュー | — | マーク・バッジ表示の追加 |

### 移行・互換

- **既に確定済みの日はそのまま**（グランドファザリング）。旧バージョンで確定台帳に載った昨日分はライブへ戻さない = 境界シフトの適用は更新後に新しく迎える日から。`finalizedCumulativeScore` の二重加算・巻き戻しを絶対に起こさないこと（`finalizedScoreReconciledThroughDayStart` の扱いに注意。必要なら1日分は「確定済みのため編集もロックのまま」と表示する）。
- 既存の過去予定・過去実績のフィールドはデフォルト値（マークなし）で自然に整合。

### EventKit（将来項目・今回は実装しない）

- 外部カレンダー同期を本格化する際も同じ原則を適用する: 同期による過去時間帯のスケジュール書き換えはクリップし、当日以降の同期反映はマーク対象とするかを docs 化してから実装。

## 8. 受け入れ基準・テスト観点

- ポリシーテスト（純粋型）: ゾーン×操作種別の許可/禁止マトリクス、マーク/バッジ/ダイアログの三位一体判定、ダイアログ発火3条件と抑制、バッジ資格（前日までの予定有無、予定ゼロ日は不獲得）、日またぎ予定の所属日。
- スコアテスト: ラチェット（追加で分母増・削除で分母不変・スコアが上がらないこと）、確定境界1日シフト、累計・ストリークの合成（確定+昨日+今日）、確定日スナップショット読みとライブ値の切り替わり。
- 移行テスト: 旧確定台帳を持つ状態で更新しても累計が変わらない・二重加算しない。
- UI: 当日朝の予定作成→マーク表示、初回変更でダイアログ→2回目は出ない、確定日削除で説明ダイアログ+スコア表示不変、ドラッグのコミット前確認で「やめる」→元位置復帰。
- 既存回帰: docs/26 Item D（過去日予定追加ガード）、Item G（ドラッグ直接操作）、ストリーク・アンロック一式。
