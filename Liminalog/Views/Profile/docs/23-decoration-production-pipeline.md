# 23. 装飾画像 制作パイプライン v0（品質・位置・被りの仕組み化）

プロフィール装飾（カードパネル/アイコンフレーム）の画像制作を、手作業の品質管理・位置調整から解放するためのパイプライン設計。
前提：[16-collection-decoration-art.md](16-collection-decoration-art.md)（美的基準・北極星＝維持）、[09-profile-design.md](09-profile-design.md)（装飾経済・語彙）、[17-monetization.md](17-monetization.md)（課金装飾はローンチ外）、[../../../../decoration-masters/README.md](../../../../decoration-masters/README.md)（マスター投入規約）。

> ステータス：**Codexプランレビュー待ち**（§4 規格逆算と §5 ツール仕様を重点レビュー）。
> 本docは docs/16 の**制作手段**（ベクター/画像ハイブリッド）を上書きする。美的基準（北極星・ランク連動・アンチパターン・受け入れ基準）は引き続き docs/16 が正。

---

## 0. 決定事項（2026-07-15 ユーザー確定）

- **カード/フレームは画像路線に一本化**。AI_TASKS §8.9b のベクター個別意匠展開（フレーム18種・カード17種）と T4 画像試作タスクは廃止。ベクターは獲得メダル/ランク意匠系に温存する。
- **目標カタログ規模：カード20種・フレーム20種以上**（現状マスター：カード24種 / フレーム62種）。フレームは大幅選抜。
- **美術館モデル**：カタログを一度揃えたら追加義務なし。定期供給をUI・文言で約束しない。新鮮さはユーザー時間（解放ラダー進行）で流れるため、暦時間の更新は不要。
- **外部有料APIは使わない**。生成手段はツール非依存の投入口として設計する（§7）。

## 1. 何を解くか

現状の3つの痛点と対応：

| 痛点 | 現状 | 解き方 |
|---|---|---|
| 品質管理が手作業 | 生成物を1枚ずつ目視 | 規格を機械検証化（§4-5）。人間は審美判定だけ |
| 位置調整が手作業 | フレーム中心ずれ等を手で補正 | アルファ解析で検知＋補正提案（§5-2） |
| 増えるほど見た目が被る | 62フレームで類似が多発 | 類似度の自動検知＋コンセプトスロット制（§5-4, §7） |

## 2. スコープ

- **対象**：プロフィール装飾のフレーム（マスター1024×1024）とカードパネル（マスター2048×1365）の画像。
- **対象外**：テーマ（コード定義・容量ゼロ）、獲得メダル/ランク意匠（ベクター）、課金装飾（ローンチ外。ただし将来販売する場合も同じパイプラインを通す）。

## 3. 全体フロー

```
Stage 0  規格の逆算・固定（Codex）
   ↓
Stage 1  検証・補正・シート生成ツール実装（Codex）
   ↓
Stage 2  既存86マスターの選抜（Claudeプレスクリーン → ユーザー最終判定）
   ↓
Stage 3  欠員スロットの再生成（プロンプト集 → 生成 → 自動検証 → 判定）
   ↓
Stage 4  出荷・凍結（imageset再生成・カタログ/ラダー整合・以後は美術館運用）
```

## 4. Stage 0：規格（コントラクト）の逆算と固定

規格値は頭で決めず、**出荷済み・ユーザー承認済みの優良マスターから機械計測で逆算**し、確定値を本節の表に追記して固定する。

### 4.1 フレーム規格（逆算対象）

| 項目 | 内容 | 確定値 |
|---|---|---|
| 寸法・透過 | 1024×1024・アルファ必須 | 確定済み |
| 中央クリアランス円 | アバターが見える中央領域。alpha≒0 の内接円半径の下限 | Stage 0 で逆算 |
| リング重心センタリング | 有効画素（alpha>閾値）の重心と画像中心の許容ずれ | Stage 0 で逆算 |
| 有効画素バウンディング | リングが端で切れていないか / 余白すぎないか | Stage 0 で逆算 |

### 4.2 カード規格（逆算対象）

| 項目 | 内容 | 確定値 |
|---|---|---|
| 寸法 | 2048×1365 | 確定済み |
| テキストセーフゾーン | 実UI（`ProfileComponents` のカード表示）のテキスト矩形をマスター座標系に転記 | Stage 0 で実UIから計測 |
| セーフゾーン busyness | 領域内の輝度分散・平均輝度の許容帯（文字が読める背景か） | Stage 0 で逆算 |

### 4.3 既知の不整合の解消

- `decoration-masters/README.md` はカード出荷幅 **1280px**、`Scripts/generate-decoration-assets.sh` は **1600px**（`CARD_TARGET_WIDTH`）。実UIの最大表示幅（@3x）から正を決め、README・スクリプト・本docを揃える。

## 5. Stage 1：検証・補正ツール（Codex実装）

リポジトリ慣例（`Scripts/validate-storekit-config.swift`）に合わせ、**外部依存なしの Swift スクリプト（CoreGraphics/CoreImage）＋zshラッパー**で実装する。名称仮：`Scripts/validate-decoration-masters.swift`。

1. **基本検査**：寸法・カラースペース・アルファ有無・ファイル名規約（`profile_card_<id>_panel` / `profile_frame_<id>`）・カタログ（`ProfileDecorations.swift`）との突き合わせ。
2. **フレーム位置検査＋補正提案**：中央クリアランス・重心センタリングを計測。ずれは補正変換（平行移動・スケール）を**提案出力**し、`--apply-centering` を明示した時だけマスターを書き換える。既定を報告のみにする理由：月桂冠など**意図的非対称デザインを自動補正で壊さない**。
3. **カードセーフゾーン検査**：§4.2 の領域の輝度統計が許容帯に入るか。
4. **被り検知**：dHash/aHash＋カラーヒストグラム距離で全ペア類似度を計算し、閾値超えをクラスタとして報告。新規候補は既存カタログとの類似も検査。
5. **コンタクトシート生成**：HTML 1枚に「マスター原画／**実表示合成モックアップ**／検査結果／類似クラスタ／keep-drop記入欄」を全件並べる。フレームはサンプルアバター円に重ね、カードは実UI相当のテキストを載せて合成する。**審美判定は必ず合成後の見た目で行う**（原画単体で判定しない）。

検証：既存86マスターでの実行に加え、故意に壊したフィクスチャ（中心ずれ・クリアランス侵食・busyセーフゾーン・ほぼ同一ペア）で検知することをテスト化。

## 6. Stage 2：既存86マスターの選抜

1. Codex がコンタクトシートを生成。
2. Claude が視覚プレスクリーン：破綻・アーティファクトの摘出、類似クラスタごとの代表推薦、keep / drop / 再生成 の推奨リスト作成。
3. ユーザーが最終判定（目標：カード20種以上・フレーム20種以上を満たす）。
4. **グランドファーザリング確認**：解放スケジュール上の位置と突き合わせる。序盤アイテム（解放者がいる可能性が高い）は「**同ID・意匠差し替え**」を優先し、IDごとの削除は解放実績が事実上ないラダー深部に限る。`UnlockRules` の閾値再割当が必要になったら別タスクに切り出す。
5. drop 分は README 規約どおり **マスター／imageset／カタログの3点セット**で削除する。

## 7. Stage 3：再生成（欠員の補充）

### 7.1 コンセプトスロット制（被りの根本対策）

- **1モチーフ＝1枠**。生成前にスロット（id・モチーフ一行定義・docs/16 語彙）を本docに追記してから作る。
- 同一プロンプトのバリエーション量産をカタログに複数入れない。類似度検査（§5-4）が最終防衛線。

### 7.2 生成手段（2案並走・投入口は共通）

| 案 | 内容 | 備考 |
|---|---|---|
| **A：ユーザー手動生成（既定）** | Claude がスロットごとの規格準拠プロンプト（解像度・透過・構図・スタイル語彙）を用意し、ユーザーが好みのツールで生成して `decoration-masters/` へ投入 | 数ヶ月前より生成モデルの品質は向上している前提で、プロンプト品質も上げ直す |
| **B：ローカル生成の試作（任意）** | mflux（FLUX / Apple Silicon）等の無料ローカルモデルを導入し、Codex がバッチ生成→自動検証→合格分だけシート掲載 | 有料API不使用の制約を満たす唯一の自動化路線。モデルDL数十GB・1枚数分。装飾オーナメント品質が実用に達するかは試作で判断 |

どちらの案でも、投入後の経路は同一：**validator → 実表示合成モックアップ → ユーザー判定 → 出荷**。

## 8. Stage 4：出荷・凍結

- `Scripts/generate-decoration-assets.sh` で imageset 再生成。HEIC化などの容量削減は別タスク（装飾アセット削減）と合流可。
- カタログ・解放ラダーの整合、ギャラリー実機確認。
- 完了後は**凍結**：以後の追加は「スロット定義の追記 → 同パイプライン」のみ。「毎月新登場」等の供給約束は置かない（美術館モデル）。

## 9. 受け入れ基準

- カード20種以上・フレーム20種以上が validator 全PASS。
- 類似度上位ペアがすべてレビュー済み（意図的なシリーズものはその旨を記録）。
- 実表示合成モックアップでのユーザー目視承認。
- `ProfileDecorations` 出荷アセット合計が現状 86MB から大幅減（目標 30MB 以下、HEIC化込みなら 15MB 以下）。
- 既存ユーザーの解放済み装飾が消えない（グランドファーザリング）。

## 10. 役割分担

| 担当 | 仕事 |
|---|---|
| ユーザー | 審美の最終判定（選抜・新規承認）。A案の場合は生成実行 |
| Claude | 生成プロンプト集・視覚プレスクリーン・シートレビュー支援・本docの更新 |
| Codex | Stage 0-1 のツール実装・バッチ実行・Stage 4 出荷 |
